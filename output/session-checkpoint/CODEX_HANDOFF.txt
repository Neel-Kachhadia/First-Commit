BOUNDARY-HARDENING RESULT (pre-existing leftover background run from

hardening.spec.ts's Resize-at-boundary test waited a flat 150ms after
setViewportSize before reading ScrollTrigger start/end via getTrackBounds.
GSAP's own resize handler debounces its refresh long enough that 150ms
isn't reliable - stale (pre-resize) bounds exceed the new, shorter
document height, window.scrollTo() clamps short, and the test's own

full 60s timeout. This is a TEST bug, not an app bug (confirmed via a
standalone repro script: bounds correct themselves within ~1-6s
asynchronously, and calling window.ScrollTrigger.refresh() immediately
after setViewportSize resolves them synchronously in ~40ms). Fix: added
an explicit page.evaluate(() => ScrollTrigger.refresh()) call right after
setViewportSize, before the existing 150ms settle wait, in
tests/visual/boundary-hardening.spec.ts (1 edit, ~L102-110).
