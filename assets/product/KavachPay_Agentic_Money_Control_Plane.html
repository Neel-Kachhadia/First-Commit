01 · Product thesis

What KavachPay actually is

KavachPay is not a payment gateway, not a UPI clone, not a wallet, and not a new mandate protocol. It is the stateful control plane above agentic-payment protocols and payment rails.

One-sentence pitch: Existing agent-payment protocols can prove that a transaction was authorized; KavachPay governs the continuously changing financial authority of an ecosystem of autonomous agents — who may spend, how much remains, what can be delegated, when step-up approval is required, and what happens when authority is revoked.

02 · Problem

AI agents can act faster than humans can supervise financial authority

Agentic commerce is moving from “AI recommends” toward “AI acts.” Payment protocols are adding trusted-agent recognition, mandates and verifiable intent. The unsolved operational question is broader: once a user delegates authority to several agents over time, who tracks the aggregate financial state?

The user problem

  • Users cannot easily see the total spending authority currently held by all of their agents.
  • Delegation chains can become hard to reason about: User → Shopping Agent → Grocery Agent → Delivery Agent.
  • A per-transaction limit does not automatically enforce a monthly or weekly cumulative budget under concurrency.
  • Revoking a parent authority must invalidate descendant authority immediately.
  • Agents can attempt transaction splitting, retries, duplicate calls or context changes after the original approval.
  • When something is blocked, users need an exact reason — not “AI risk score 83.”

The developer / platform problem

  • Different agentic-payment protocols represent trust and intent differently.
  • Payment providers expose different request, webhook and idempotency semantics.
  • Existing tool authorization can be stateless while finance requires durable, transactional state.
  • Protocol receipts prove individual events; operators still need cross-agent history, exposure and replay.
  • Developers need safe test scenarios before autonomous money movement is enabled in production.
Why now: AP2 v0.2 supports autonomous human-not-present flows and explicitly leaves agent-to-agent mandate delegation outside its current specification. Visa Trusted Agent Protocol is public. Mastercard is pushing Verifiable Intent and Agent Pay. In India, NPCI is reported to be developing authorization/registry infrastructure for agentic UPI. This makes the control layer timely without pretending the standards are finished.
03 · Exact product

What are we building?

Connect agent→Create intent→Compile contract→Delegate authority→Authorize / step-up / deny→Execute sandbox payment→Record receipt→Replay / revoke

Consumer / business control plane

Web app where the principal creates money mandates, watches active authority, approves step-up requests, revokes authority, inspects payment decisions and replays the exact causal chain.

Developer runtime

Gateway/API that receives agent intents and protocol artifacts, normalizes them into a Financial Intent Contract, performs deterministic stateful checks, invokes AgentCore policy where useful, and forwards approved requests to PSP sandbox adapters.

Protocol adapter layer

AP2 adapter first. Visa TAP verifier as a second proof-of-interoperability adapter if time allows. Mastercard/NPCI are treated as roadmap integrations unless a public developer interface is actually available.

Evidence plane

Every decision produces a tamper-evident Decision Receipt: principal, agent path, mandate version, evaluated constraints, state before/after, protocol artifacts, payment provider event and signature/hash references.

05 · Feature set

What we will showcase

1. Financial Authority Graph

Live DAG of principals, agents, child agents, grants, inherited constraints, expiry and remaining capacity.

2. Mandate Builder

Natural-language intent → structured contract → human review → signed/activated authority.

3. Delegation Accounting

Child authority can only be carved out of the parent's remaining authority. No privilege amplification.

4. Cumulative Budget Engine

Weekly/monthly budgets and rolling windows enforced transactionally under concurrent agent actions.

5. Step-Up Approval

Pause high-value or context-changing actions and request one-time human approval without increasing the permanent limit.

6. Revocation Cascade

Revoking a parent invalidates its descendant authority immediately and blocks dependent in-flight requests.

7. Split-Transaction Defense

Detect attempts to bypass a limit by splitting one economic action into smaller requests across a time window.

8. Financial Blast Radius

Compute the maximum reachable autonomous exposure under current contracts and delegations.

9. Protocol Adapter Inspector

Show AP2 mandate fields and how they become a normalized KavachPay Financial Intent Contract.

10. Payment Sandbox Execution

Execute approved intents against Razorpay/Cashfree test mode and validate signed webhooks.

11. Causal Replay

Scrub through a transaction and reconstruct authority, state, policy decision, provider request and webhook result.

12. Attack / Failure Lab

Run duplicate, replay, revoked-agent, price-change, merchant-change, concurrent spend and split-payment scenarios.

08 · Core engineering

The technical spine

1. Financial Intent Contract

The normalized object that decouples user intent from any one protocol or PSP. Protocol adapters may create it, but only a user-approved/signed or explicitly trusted workflow can activate it.

{
  "contract_id": "fic_01",
  "principal": "user_123",
  "budget": {"currency":"INR","limit":4000,"window":"P7D"},
  "single_transaction": {"step_up_above":1500,"hard_max":4000},
  "categories": {"allow":["GROCERY"],"deny":["ALCOHOL","GAMBLING"]},
  "merchant_rules": {"deny":[],"allow":[]},
  "delegation": {"enabled":true,"max_depth":2,"max_children":5},
  "expiry": "2026-09-20T23:59:00+05:30",
  "status": "ACTIVE"
}

2. Authority invariants

No amplification

A child grant can never create spending capacity beyond the residual authority of its parent. Delegation transfers/scopes authority; it does not mint new money.

Atomic consumption

Two agents racing to use the last ₹500 must not both succeed. DynamoDB conditional transactions reserve authority before PSP execution.

Revocation closure

A revoked or expired ancestor makes descendant authority non-executable even if a child record has not yet been physically deleted.

Replay safety

Intent IDs, protocol transaction IDs and PSP idempotency/event IDs prevent a valid authorization from being replayed into a second economic effect.

validate_identity_and_signature()
  ↓
resolve_active_authority_path()
  ↓
reject_if_revoked_or_expired()
  ↓
check_merchant_category_time_constraints()
  ↓
check_single_transaction_cap()
  ↓
check_cumulative_and_rolling_budget()
  ↓
check_split_transaction_pattern()
  ↓
reserve_budget_atomically()
  ↓
AgentCore/Cedar secondary authorization
  ↓
ALLOW | STEP_UP | DENY
  ↓
if ALLOW: execute PSP sandbox + wait for authenticated webhook
  ↓
commit final economic state / compensate reservation on failure

4. Blast-radius computation

Represent authority as a directed acyclic graph. Every edge carries a derived grant. Compute the maximum executable exposure using a topological traversal with ancestor caps; descendants are not added on top of a parent when they merely consume that parent's capacity. Cycles are rejected at grant creation.

5. Split-payment evasion

Maintain rolling counters by mandate, merchant, category, agent subtree and short time window. A sequence of ₹1,000 + ₹1,000 + ₹1,000 can trigger step-up/deny even when each individual request is below a ₹1,500 threshold if the economic policy says the cumulative action exceeds authority.

13 · Risks

The judge attacks we must survive

“Isn't this AP2?”

Answer: AP2 secures individual agent-payment mandates and receipts. KavachPay is the runtime state layer across agents and transactions: delegation lineage, cumulative budget consumption, revocation propagation, blast radius and cross-provider replay. AP2 is an input, not our product.

“AgentCore already has Cedar.”

Answer: Exactly. We use it. Cedar authorizes a tool call. KavachPay decides the financial context that the authorization must respect: remaining budgets, ancestor grants, revocation, split-payment history and protocol state.

“Are you actually doing UPI agent payments?”

Answer: No. NPCI's agentic framework is emerging, and we found no public UPI agent execution API for a hackathon team. Our demo uses live first-party agent telemetry plus PSP test environments; UPI/UAP is a future adapter.

“Is this real money?”

Answer: No. Razorpay/Cashfree sandbox. The control-plane state, authorization, delegation, revocation, concurrency and webhook validation are real; the payment economic effect is simulated and labeled as such.
